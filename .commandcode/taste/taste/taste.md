# Taste
- Communicates in Vietnamese and expects assistant responses in Vietnamese. Confidence: 0.9
- Dislikes when the assistant gets stuck repeating the same action (e.g., waiting/polling on a long-running command) without making progress; wants the assistant to recognize stuck loops, switch strategy or stop, and report/ask the user instead of continuing to repeat. Confidence: 0.9
- Prefers project reviews that are thorough, serious, and feature-by-feature, explicitly assessing whether each feature genuinely solves real user problems; wants the review structured with backend logic evaluated first, then the frontend UI (user-friendliness, visual quality, clutter/component density). Confidence: 0.8
- Prefers that review/analysis results be written into a markdown file for record-keeping. Confidence: 0.8
- Expects full-project code reviews to cross-reference docs/review logs/feature specs against the actual code, verify every feature/API/method actually works (running tests/builds to confirm real state), and actively hunt for dangerous security bugs and dead code on both backend and frontend. Confidence: 0.8
- Selected Opus 5 (1M context) as the default model for new sessions. Confidence: 0.7
- Prefers using the project's local binaries / npm scripts (`npm test`, `node_modules/.bin`) over `npx` (which can pull a cached vitest lacking project deps like jsdom), and checks `node_modules` actually contains the needed packages before running. Confidence: 0.7
- Prefers evidence-first debugging: before batch-fixing many failing tests, wants the root cause proven or eliminated first (e.g., ruling out environment artifacts such as npx-cached deps mismatching the lockfile) to avoid "fixing" correct tests and creating regressions. Confidence: 0.9
- Prefers standardizing the dev environment across machines for reproducible test results: pin the Node version (`engines` in package.json + `.nvmrc`), document `npm ci` (from lockfile) rather than `npm install`, and add CI guards (e.g., a `test:ci` script, forbidding `npm install` in CI). Confidence: 0.8
- Wants to be asked targeted clarifying questions (e.g., exact Node version, JSON reporter output) and to approve staged steps before the agent executes a multi-step plan. Confidence: 0.6
- Prefers features planned/designed for independent development: each feature should be decoupled from others so they can be built in parallel without mutual interference or cross-feature imports. Confidence: 0.85
- Enforces a "5 integration points" rule: a feature may touch only a minimal, well-defined set of integration points — exactly one line each in `frontend/src/router/routes.ts` (route entry), `frontend/src/appTabs.ts` (tab entry), `frontend/src/views/admin/AdminPanelView.vue` (admin tab line, if applicable), `ApplicationDbContext` (DbSet line), and `Program.cs` (DI line, if applicable). Confidence: 0.85
- Requires append-only migrations: a feature's migration only ADDs new tables/columns; never modify an existing migration, and never run `dotnet ef database update` from another feature's migration. Confidence: 0.85
- Requires per-feature git branches with sequential merging (one feature = one branch, merged in turn) to keep work streams isolated. Confidence: 0.8
- Requires feature-level test isolation: each feature gets its own test file and must not modify another feature's tests. Confidence: 0.8
- Prioritizes small features first and treats the largest feature as the first candidate to cut under time pressure, preferring to update documentation to match reality rather than ship an incomplete feature. Confidence: 0.8
- Prefers daily/status reports to be grounded in the actual git history of the specified repos — derives "what I did yesterday" from real commits rather than just echoing the provided template, and flags template items that don't match actual commits. Confidence: 0.7
